# Twist response

Read this when a twist arrives. A twist is an official change to the
problem. Adapting to twists is a judging criterion and the basis of the
Best Shift Adapter award ("bent the furthest without breaking").

| Twist | Released (PT) |
|---|---|
| 1 | Fri 2026-10-16 23:30 |
| 2 | Sat 2026-10-17 04:30 |

The organizers lifted the original six-hour response limit (user report,
Sat 2026-10-17 09:50 PT): all three responses are submitted together with
the Devpost submission, due Sat 2026-10-17 22:00 PT. Changes are announced
on WhatsApp; use the time actually announced.

## Steps

1. Capture: copy the twist text verbatim into its section of
   [../problem/twists.md](../problem/twists.md) with the release time.
2. Assess: which assumptions in [../problem/brief.md](../problem/brief.md)
   and which parts of [../architecture.md](../architecture.md) it breaks or
   strengthens, and what it means for the civil use and the crisis use.
3. Decide the smallest change that answers the twist visibly in the demo.
   Prefer extending the existing build over rebuilding it; the point is to
   show the build bends without breaking. Note what is deferred.
4. Implement, test, and keep `main` demo-able.
5. Write the response for the portal (what changed, why, how it shows in
   the demo) for the final submission. Submitting it is the user's action;
   draft it, do not send it.
6. Record: a change record of Type `twist` and the outcome row in
   `twists.md`.
